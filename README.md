# runbook-run

> 半年做一次的事，每次都像第一次做。
>
> 证书怎么续、面板菜单在第几层、校验文件放哪个目录、reload 之后要验哪条命令——这些都不难，难在一年只碰两次，脑子里那套流程早就凉了。

这个工具把「一篇 Markdown 笔记」变成「能一步步执行、有检查点、错了会停」的东西。零依赖，清单用 JSON 写。

## 它解决的到底是哪个问题

不是记不住，是频率太低。低频加上高风险，是遗忘的最佳配方。

我自己的做法一直是写清单：把步骤记在文档里，每次照着做，做完把新发现补进去。这么干了两年，清单从半页长到两页。问题是**清单本身不会阻止你跳步**——你看着第七条，手已经在敲第十条的命令了，因为「反正我记得」。

更麻烦的是清单里混着两类东西：一类是命令（跑一下就知道结果），一类是判断（这个日期对不对、这张证书是不是新的）。抄在 Markdown 里，两类长得一模一样，都得靠人盯着。

所以分成两种步骤：

- **命令步骤**：写清楚命令和判定条件，工具执行、工具判断过没过
- **人工步骤**：只写标题和说明，工具提示你去做，做完按回车记录

混在一起的时候，人工步骤最容易被跳过。分开之后至少有个停顿。

## 清单长什么样

```json
{
  "name": "TLS 证书轮换（源站 + 边缘两层）",
  "vars": { "domain": "www.example.com", "certDir": "/etc/nginx/cert" },
  "steps": [
    {
      "id": "precheck-public",
      "title": "看公网现在拿到的是哪张证书",
      "run": "echo | openssl s_client -servername {{domain}} -connect {{domain}}:443 2>/dev/null | openssl x509 -noout -enddate",
      "expect": { "contains": "notAfter" },
      "note": "这是唯一的验收标准。面板、监控、浏览器小锁都不算证据。"
    },
    {
      "id": "backup",
      "title": "备份现有证书文件",
      "manual": true,
      "note": "私钥不是能重新生成的东西。备份加日期后缀，别用 bak 这种名字。"
    }
  ]
}
```

字段就这些：

| 字段 | 说明 |
|---|---|
| `id` | 步骤标识，不能重复，`--only` 用它定位 |
| `title` | 显示给人看的一句话 |
| `run` | 要执行的命令，支持 `{{变量}}` |
| `expect` | 判定条件，不给就按「退出码为 0」判 |
| `manual` | 设为 `true` 表示这步由人操作，工具不执行命令 |
| `note` | 为什么要做这一步，或者做的时候注意什么 |
| `rollback` | 这步失败时该执行的补救命令 |

`expect` 支持四种：`contains`、`notContains`、`regex`、`exitCode`，可以组合。

## 跑起来

```bash
node bin/runbook.js runbooks/tls-renewal.json --list
node bin/runbook.js runbooks/tls-renewal.json --dry-run
node bin/runbook.js runbooks/env-check.json --yes
node bin/runbook.js runbooks/tls-renewal.json --only precheck-public
```

交互模式下，每一步停下来等你：

```
[1/9] 看公网现在拿到的是哪张证书  (precheck-public)
  这是唯一的验收标准。面板、监控、浏览器小锁都不算证据。
  $ echo | openssl s_client -servername www.example.com -connect www.example.com:443 ...
  判定：包含「notAfter」
  回车执行，s 跳过，q 退出：
```

执行完会显示输出和判定结果。失败就停下，把这一步配的回滚命令打出来：

```
[2/3] 会失败的一步  (bad)
  $ node -e "process.exit(3)"
  判定：退出码 0
  fail  期望退出码 0，实际 3  122ms

  回滚命令（需要你手动执行）：
  $ cp -a /tmp/a.bak /tmp/a

  在「会失败的一步」这一步停下，后面的步骤没有执行。
```

非交互环境（比如 CI 或者脚本里调）必须加 `--yes`，否则直接报错退出。这是故意的——不给个明确的确认，就不执行。

## 三个刻意的设计

**回滚只打印，不执行。** 自动回滚听起来很美好，实际上是把一个不确定状态换成另一个不确定状态。这一步为什么失败、系统现在处于什么状况，只有人能判断。工具能做的是把命令准备好摆在面前，不能替你按下去。

**危险命令要额外一层放行。** 清单里出现 `rm -rf /`、`mkfs`、`dd of=/dev/`、覆盖 `/etc/` 这类命令时，即使加了 `--yes` 也会被拦下来，要求再明确一次 `--force`：

```
有步骤包含危险命令：
  boom: 递归删除根目录、递归强制删除
    rm -rf /

确认无误请加 --force 重新执行。
```

这层拦截是给「从别人那儿拷贝来的清单」准备的。你不知道那份清单里埋了什么。

**`manual` 步骤永远不执行命令。** 有些事就该人干——在控制台点按钮、判断一个日期对不对、决定要不要继续。清单里给这类步骤写 `run` 命令，反而会诱导人无脑回车。所以干脆不允许写。

## 内置两份清单

`runbooks/tls-renewal.json` 是完整的一套证书轮换流程，九步，源站四步加边缘三步加两次验证。它本身就是一份可用的作业指导书，就算不用这个工具，照着一条条做也行。

`runbooks/env-check.json` 是跨平台的环境自检，只读，四个检查：Node 版本、系统时间与 UTC 偏移、工作目录、目录可写。放在任何一次动手之前跑一遍，确认自己不是在错误的机器上操作。

样本清单里我留了不少 note，那些都是踩过之后补的。比如证书那套里有一条：「进度条在转不代表没生效，证书早就下发到能服务的那批节点上了，判断生效只看公网握手」——这条是当年在控制台前干等了十分钟换来的。

## 边界

**它不调度、不重试、不并发。** 一次一份清单，一步一步走。批量编排是另一个问题。

**它不记录系统状态快照。** 日志里只有「某步执行了、结果如何、耗时多少」，没有执行前后的现场。要做审计追踪，需要另外挂。

**`{{变量}}` 只做字符串替换。** 不做默认值、不做表达式、不做条件分支。清单一旦开始需要 if，就说明它该变成脚本了，别硬塞。

**它假设你在一台能直接操作的机器上。** 跳板机、容器、SSH 到另一台再跑——这些场景它帮不上，它只会在当前 shell 里执行。

**命令是 `spawnSync` 跑的，`shell: true`。** 所以管道、重定向、`&&` 都能用，但也意味着清单里的命令有完整的 shell 权限。清单要当代码一样审。
